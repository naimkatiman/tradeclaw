## Headline — the 08:17 fire is the *missed 09-10 run catching up*, not an early 09-11 run, and catch-up runs are RUN-dated, which is why 09-10 can never have a standup

Windows Task Scheduler does not fire a trigger *before* its scheduled time. A 09:30 trigger cannot
produce an 08:17 run of 09-11. The only mechanism consistent with its semantics is
"run task as soon as possible after a scheduled start is missed": the host was asleep across
09-10 09:30, woke this morning, and the queued 09-10 run fired at 08:17 today.

This is not an inference from one case. The launcher log directory records **five** early-morning
off-slot fires, and every single one is immediately preceded by at least one date with zero logs
for any project:

| Off-slot fire | Preceding date(s) with no log for ANY project | Same-day 0930 run followed? |
|---|---|---|
| `daily-2026-07-27_0615` | 07-24, 07-25, 07-26 | yes — `daily-2026-07-27_0930` |
| `daily-2026-08-20_0606` | 08-14 … 08-19 | yes — `daily-2026-08-20_0930` |
| `daily-2026-08-26_0614` | 08-25 | yes — `daily-2026-08-26_0930` |
| `daily-2026-09-03_0724` | 09-02 | yes — `daily-2026-09-03_0930` |
| `daily-2026-09-11_0817` (this run) | 09-10 | **predicted, not yet observed** |

Five for five. `daily-2026-09-06_1634` is the control case that fits the same rule from the other
side: the host woke *after* the 09:30 slot that day, so the catch-up and the on-slot run collapsed
into one fire and there was no second run.

### The consequence that has been invisible until now: the catch-up is run-dated

The 09-06 standup got the mechanism right ("missed-run catch-up on wake") and stopped there.
What it did not state is what the catch-up *writes*. The launcher stamps the output path with the
**run** date, not the missed date. Proof already in the record: the Friday 09-04 weekly caught up on
Sunday 09-06 and produced `docs/research/weekly-research-2026-09-06.md` — there is no
`weekly-research-2026-09-04.md` and there never will be.

Therefore `docs/automation/standups/2026-09-10.md` is **terminal-absent**. Not deferred, not
pending, not recoverable. This satisfies the 09-07 Class D guard properly: the run is reportable as
lost because the date has passed, the catch-up for it has already fired (this run), and that
catch-up wrote a 09-11 path. The claim is terminal on evidence, not on a glob returning nothing.

`699e8cd3` (07:40) landed the catch-up standup, and `5eae4838` (09:39) landed the second run whose

on 08-26. So a double-fire day costs a duplicated artifact, not lost work — worth stating plainly,
because the opposite conclusion ("five runs of wasted work") is the tempting one and it is wrong.

## Lessons (for `loops/state/tradeclaw.STATE.md`)

The state-file append is denied at the harness sensitive-file layer even after gateguard clears it
(two-layer pattern, re-confirmed 09-07 and 09-08). Lessons live here for copy-paste.

1. **A scheduler cannot fire early — an off-slot run before the nominal time is a catch-up for a
   missed slot.** Establish which slot it is catching up on before dating anything.
2. **Catch-up runs are RUN-dated, so the missed day's artifact never exists.** Proven twice:
   the 09-04 weekly became `weekly-research-2026-09-06.md`; 09-10's daily became this file. A
   missed date is terminal-absent the moment its catch-up fires on a later date.
3. **A catch-up followed by an on-slot run the same day writes one path twice.** Supersession, not
   loss — the earlier commit survives in history. Do not report double-fire days as wasted work.
4. **Report a count with the path expression that produced it.** `+57 -2` over `regime-*` and
   `+118 -30` over `scripts/research/` describe the same unchanged tree. Third instance of this
   class after `--porcelain` vs `-uall` (09-07) and "green at <sha>" (09-08/09-09).
5. **Separate "the loop failed" from "the loop never ran" numerically, not rhetorically.** 93% on
   fire-days vs 68% on calendar days over 41 days makes the owner-availability call obvious in a
   way five standups of prose did not.

Three shas, all on 2026-07-15, 56 days ago. Now the part that matters:

```
git merge-base origin/main HEAD      ->  524fc44a8999bf69b6c56f0c44caf25efa5bedd0
git rev-list --count 524fc44a..HEAD  ->  71
git rev-list --count origin/main..HEAD -> 71
```

**`524fc44a` is the fork point.** The single green CI run on this branch is on the commit the branch *begins at* — the last commit it shares with `main`. The two counts are equal because the merge-base and the CI baseline are the same commit. Every one of the 71 branch-unique commits is CI-unverified, and none will become verified, because nothing here opens a PR to trigger a run.

### Why this is the 09-08 error class, one degree worse

09-08 corrected a claim that main was "green across CI, Docker Publish, Docker Smoke and Weekly GitHub Pulse" at `51f94081` — only two of the four had run on that sha. It named the distinction: *"green at `<sha>`" is not the same claim as "green somewhere in this history."*

The branch case adds a third, sharper form. Here the green sha is not merely a different commit in the history — it is the commit that contains **none of the work being asked about**, by construction. A branch filter is the natural way to ask "is my branch green," and on a branch that never re-runs CI it answers with rows describing the shared ancestor. The query is not wrong; it answers a question adjacent to the one asked, and the adjacency is invisible in the output. Nothing in `gh run list --branch X` prints "this sha predates all of your work."

Guard, stated as a rule the next run can apply mechanically: **before quoting a CI verdict, compare the run's sha to the sha in question.** If they differ, resolve the relationship — ancestor, descendant, unrelated — and say which. On a branch, additionally compare against `git merge-base`; if the CI sha *is* the merge-base, the honest statement is "no CI coverage," not "green."

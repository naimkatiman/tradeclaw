## HEADLINE — Class B2 is self-healing on a persistent branch, and yesterday's escalation is corrected

The 09-14 standup opened its report with the first confirmed Class B2 failure in the corpus: commit `33186435` (the entire 09-13 standup) committed but never pushed, on **zero** remote refs, while the state file recorded that run as `gate verdict: PASS`. It framed the failure as severe and cited PR #160 as proof the class strands work permanently.

Both halves are now settled by measurement, and they settle in opposite directions.

### The stranded commit repaired itself in 24h 09m 07s

`git branch -r --contains 33186435` now returns `origin/feat/premium-ui-overhaul`. The commit is on the remote. Nothing rescued it by hand.

The mechanism is read off the remote-tracking reflog, not inferred:

```
fd3210f0 refs/remotes/origin/feat/premium-ui-overhaul@{2026-09-14 09:46:22 +0800}: update by push
9e8e57ce refs/remotes/origin/feat/premium-ui-overhaul@{2026-09-12 09:44:52 +0800}: update by push
```

There is **no push entry between 09-12 09:44:52 and 09-14 09:46:22**. That independently re-confirms the 09-14 finding that the 09-13 run never pushed — the reflog is a second witness to what `ls-remote` showed yesterday.

Commit timestamps close it:

```
fd3210f0  2026-09-14 09:46:09 +0800   (the 09-14 standup)
33186435  2026-09-13 09:37:15 +0800   (the stranded 09-13 standup)
```

The 09-14 run committed at 09:46:09 and pushed 13 seconds later at 09:46:22. Because `33186435` is the direct parent of `fd3210f0`, that single push carried the stranded commit with it. Exposure window: **09-13 09:37:15 → 09-14 09:46:22, i.e. 24h 09m 07s**, then closed automatically.

This is a structural property, not luck. The daily loop always commits to the same long-lived branch, so any commit-without-push is a *parent* of the next run's commit, and git pushes ancestors by definition. A commit-only run on a persistent branch cannot strand work for longer than one loop interval unless the branch itself stops being pushed.

### PR #160 is a different failure class — measured, not argued

Yesterday's standup said PR #160 "exists solely to rescue 5 standups stranded by this same class." It is not the same class. Evidence:

- `git ls-tree -r --name-only origin/docs/rescue-stranded-standups docs/automation/standups` carries `2026-07-05`, `07-06`, `07-07`, `07-08`, `07-11`.
- Those five filenames are **absent** from `feat/premium-ui-overhaul` (`git ls-tree -r HEAD docs/automation/standups | grep -E '2026-07-(0[5-9]|1[01])'` returns nothing).
- They are **absent** from `origin/main`, whose standup directory holds exactly 6 files and ends at `2026-07-02`.

Those five were written on their own per-run `loop/standup-*` branches. No later run ever commits a child onto those branches, so no later push can carry them. That is why they needed a hand-built rescue branch and why #160 has stayed open 65 days.

The distinction, stated so a future run can act on it:

| | mechanism | repair | evidence |
|---|---|---|---|
| **B2-transient** | commit-only on the *persistent* loop branch | automatic at the next run's push | `33186435`, closed in 24h 09m |
| **B2-terminal** | commit on a *per-run* branch never pushed again | needs a manual rescue branch + PR | 07-05..07-11, PR #160, still open |

The 09-14 run's severity call was wrong for the case it actually hit. Its underlying observation — that the 09-13 run stopped at commit — was right, and is re-confirmed here by a second instrument.

### What genuinely stays broken

The contract conflict that caused it is untouched. Re-read at source this run:

- `project-loops/SKILL.md` daily step 5, verbatim: `Commit to the allowed branch by explicit path. Stop.` No push clause.
- The injected standup prompt STEP 3.3/3.4: `Push with -u` and `Open or update a PR`.

A run can satisfy either and fail the other. And the referee still cannot tell:

```
gate.ps1:44   # 3. branch safety (only when a git repo path is supplied). `branch --show-current`
gate.ps1:51   $branch = (& git -C $RepoPath branch --show-current)
```

Those two lines are the file's **only** `git` calls. `gate.ps1` never inspects commit, push, or remote state, so it cannot distinguish a pushed run from a commit-only one, and it cannot distinguish B2-transient from B2-terminal. It passed the 09-13 run and would pass a terminal one identically. This is `loop-gate-is-filesystem-only` restated with a sharper edge: the gate's blind spot is survivable on this branch and fatal on a per-run branch.

Actionable consequence for any future loop that is told to use a per-run branch: pushing is not optional there, because no later run will rescue you.

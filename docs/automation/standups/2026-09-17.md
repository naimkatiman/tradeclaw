## HEADLINE — `integrity: true` is a full replay of the NAV series, not a hash check, and that narrows yesterday's own caveat

Yesterday this loop verified the hash chain client-side and honestly stated its limit: *"a payload edited **and** re-chained from that row forward would still pass."* That caveat was correct about the instrument used. It understates what the server does.

Read at source — `git show origin/main:apps/web/lib/d1-alpha-ledger.ts`, `readD1AlphaReport` — every row goes through three independent gates before it is allowed into `verified`:

1. **Chain linkage.** `snapshot.previousHash !== previous.rowHash` → `throw 'hash chain does not link to the prior row'`. Genesis must have `previousHash === null` or → `throw 'genesis row has a previous hash'`.
2. **Column projection.** `verifyProjection()` cross-checks **31 stored DB columns** against the decoded payload — both fingerprints, both sleeve closes, transition actions and prices, engine exposures, positions, sync flags, four NAVs, four cost/funding increments, and the closed-trade increment. Any mismatch → `throw '<field> projection mismatch'`.
3. **Full replay.** The payload is **recomputed** — `advanceD1AlphaSnapshot(verified[index-1].payload, observationFromPayload(snapshot.payload))` — and compared canonically:

```
if (canonicalD1AlphaPayload(recomputedPayload) !== canonicalD1AlphaPayload(snapshot.payload))
  throw new Error('snapshot state or modeled-cost math does not reproduce');
```

Gate 3 is the one the corpus has been under-claiming for five weeks. `integrity: true` does not mean "the hashes line up." It means **the entire 39-row NAV series re-derives from the stored raw observations under the frozen cost model, row by row, and reproduces byte-for-byte.** The edit-and-re-chain attack yesterday could not exclude would have to also rewrite the raw closes, the exposures, the transitions and the cost/funding increments so that the modeled-cost math still reproduces — i.e. it would have to be a consistent forgery of the inputs, not a tampering of the outputs.

**What still is not claimed.** I cannot compute SHA-256 in-run, so I have not verified that `rowHash` is the true digest of its payload. And I read `origin/main`, which is the deployed ref but is not proof of what is running. Both limits stated rather than papered over.

## What `cadence: true` actually certifies — decoded at source, and it is not what it reads like

`cadence` is the one observation check no run has ever examined. Read at source:

```
cadencePassed   = unresolvedCadenceGaps === 0 && integrityPassed
integrityPassed = verified.length === rows.length && errors.length === 0
```

`unresolvedCadenceGaps` is incremented from exactly two places, and they mean different things:

**(a) A stored mid-chain gap.** `gap !== D1_ALPHA_DAY_MS` → increments by `Math.max(1, Math.floor(gap / DAY) - 1)` and **throws**. The throw is caught into `errors[]` and the loop **`break`s** — so a stored gap does not merely fail cadence, it stops verification at that row. `verified` holds the prefix, `integrityPassed` goes false, and metrics recompute over the prefix.

**(b) Tail staleness.** `expectedLatestClosedBar = floor(now / DAY) * DAY - DAY`; if the latest verified bar is older than that, the shortfall in whole days is added.

Three consequences, none of them previously recorded:

1. **The flag is decodable.** `cadence: false` **with** `integrity: true` can only come from branch (b) — it means *the daily commit stopped*. `cadence: false` **with** `integrity: false` means a stored gap. Two distinct failures behind one boolean, and the pair tells you which.
2. **`cadence: true` does not mean "a snapshot exists for today."** Worked twice against real timestamps: latest bar `1789516800000` (2026-09-17T00:00:00Z). Read at 2026-09-18T06:00Z with today's cron *failed* → `expectedLatestClosedBar` = 2026-09-17T00:00:00Z; `latest < expected` is **false** → 0 gaps → **cadence still passes**. Read at 2026-09-19T06:00Z → expected 2026-09-18 → gap 1 → cadence fails. **The detector absorbs exactly one missed commit day.** That grace is the intended slack between a bar closing and the cron committing at 00:02 UTC — not a defect, but it means cadence is a two-day-late alarm, and no run should read it as "the pipeline ran today."
3. **`snapshots = calendarDays + 1` re-derives on a fourth read.** `(1789516800000 − 1786233600000) / 86400000 = 38` exactly; rows `= 39`; `verifiedRows = 39`. 38 intervals, 39 fenceposts. `calendarDays` stays the binding observation constraint.

## `closedTrades` — the counting convention is closed at source, and the memory caveat resolves

The memory `d1-alpha-closedtrades-minimum-unreachable` carries an explicit open instruction: *"Verify this before reusing the number — the finding inverts on it."* Resolved this run, at the live protocol rather than the research artifact.

`closedTrades` is set in exactly one branch of `d1-alpha-protocol.ts`:

```
if (position === 'LONG') {
  ...
  if (transition?.action === 'EXIT_GATE' || transition?.action === 'EXIT_STOP') {
    cost = nav * D1_ALPHA_SIDE_COST_FRACTION;
    nav -= cost;
    position = 'FLAT';
    closedTrades = 1;            // ← the only assignment
  }
```

- It counts **exits only**, never entries. One completed round trip per sleeve = exactly **1**.
- Per sleeve, summed: `closedTradesIncrement = btcStrategy.closedTrades + ethStrategy.closedTrades`, validated `0…2` (`d1-alpha-ledger.ts`, `closedTradesIncrement > 2` → `throw 'closed-trade increment is invalid'`).
- Total = `snapshots.reduce((sum, s) => sum + s.closedTradesIncrement, 0)` — cumulative sleeve exits since genesis.

**This matches the memory's `150 flips / 2 = 75 closes`,** and a parity argument corroborates the division independently: starting flat, flips alternate enter/exit, so a series ending flat has an even flip count with `closes = flips / 2`, and one ending long has an odd count. BTCUSD `86` and ETHUSD `64` are **both even** — consistent only with both series ending flat, which is precisely the case where `flips / 2` is correct. `8.449` closes/yr survives verification; the `~519 day` horizon stands.

Two corrections to the horizon, in opposite directions, both named:

- **Longer than 519 days.** The live counter only increments when `prospectivePosition === 'LONG'`. An inherited historical exit takes the `synchronized` branch — *"The inherited historical position has now closed without creating a prospective trade"* — and increments **nothing**. So the ledger's first close is structurally delayed past the first prospective `ENTER_LONG`.
- **Shorter than 519 days.** `EXIT_STOP` counts as a close, and the pre-registered walk-forward modeled the EMA200 crossing only. Stop-outs are extra exits.

The defensible statement is unchanged: **the trend rule alone cannot reach 12 closes in 365 days; reachability turns entirely on stop-out frequency, the one component the walk-forward never measured.** Both sleeves are `LONG` and `closedTrades` is `0` after 39 rows — no exit has occurred in the ledger's entire life, which is exactly what a ~39.6-bar mean hold predicts. **`closedTrades: 0` is still not a pacing miss.**

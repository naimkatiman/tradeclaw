## Headline: the calibration "cache defect" is ISR on an idle endpoint, and that corrects yesterday twice

Yesterday's artifact made two claims about `/api/calibration`:

1. The edge cache does not key on the query string.
2. A fail-closed body (`totalSignals: 0`) was "served publicly for five hours."

This run's two reads support the first claim and take apart the second.

| # | URL | `updatedAt` | Age at read | `totalSignals` |
|---|---|---|---|---|
| 1 | bare URL | 2026-10-14T01:36:55.673Z | **23h 54m** | 7,606 |
| 2 | `?r=20261015b` | 2026-10-15T01:31:16.820Z | fresh | 7,634 |

Read 1 returned **yesterday's fresh body, byte-identical to the millisecond**, almost 24 hours later. Read 2 came back fresh. `/api/health` at 01:31:23.937Z returned the current second, so the deployment was live and answering throughout.

The route says why. On both this branch and `origin/main`, `apps/web/app/api/calibration/route.ts:10` sets `export const revalidate = 300; // 5-min cache`. That is Next.js ISR, and ISR does not expire bodies at 5 minutes. After 300s, the next request still gets the stale body, and that request triggers a regeneration in the background. Read 2's timestamp (01:31:16.820Z) falls between read 1 and the health probe. That fits read 1 being the trigger. The `5-min cache` comment is wrong. The 300s is a minimum age before a rebuild, and nothing caps how stale a body can get.

### What this changes

- **Yesterday's pattern was the same mechanism.** Read 1 got the stale deploy-window body, and read 2 got the regenerated one. That is ISR doing what it does, not a separate defect.
- **"Served publicly for five hours" is not supported.** An ISR entry keeps the stale body only until the first request after expiry. So that fail-closed body probably reached exactly one request: this loop's. *Inferred*, not measured. It assumes a single cache region, and a multi-region edge would split entries.
- **Inferred from the same mechanism: for about 24 hours, no request other than this loop's hit that cache entry once it had expired.** Any request after 01:41:55Z on 10-14 would have triggered a regeneration and moved `updatedAt`. It did not move until this run. The public calibration endpoint behind "Every trade verified" appears to get about zero organic traffic. Labelled inferred for the same single-region reason.
- **The brand risk is real but narrower than reported.** A visitor arriving after an idle stretch sees numbers of unbounded age. They are labelled with an honest `updatedAt`, but they are not "5-min" fresh. During a deploy window that body can be the fail-closed zero. A one-line fix (dynamic route or `Cache-Control` with an explicit ceiling, or excluding the fail-closed path from caching) is product code, so this loop does not write it. It is escalated.

Yesterday's lesson repeats with the roles swapped: 10-14 corrected 10-13's method, and today corrects 10-14's interpretation. Re-testing has to include the previous day's fresh findings, and this run did that.

## The edge cache does not key on the query string — correcting yesterday

Yesterday's artifact concluded that `?cachebust=…` yields a fresh read, and built its production numbers on that. **That conclusion is wrong**, and this run established it by execution rather than by reasoning.

Three reads of `/api/calibration`, in order, each with a different URL:

| # | URL | `updatedAt` | `totalSignals` | `insufficientData` |
|---|---|---|---|---|
| 1 | `?cachebust=20261014a` | 2026-10-13T20:34:15.418Z | **0** | **true** |
| 2 | `?probe=20261014b-second` | 2026-10-14T01:36:55.673Z | 7,606 | false |
| 3 | **bare URL** (no query) | 2026-10-14T01:36:55.673Z | 7,606 | false |

Reads 2 and 3 carry **identical millisecond timestamps**. `route.ts:137` stamps `new Date().toISOString()` per request, so two independent computations cannot collide on the same millisecond. Read 3 therefore returned the body that read 2 computed — a different URL, the same cache entry. **The query string is not part of the cache key.**

That reframes yesterday's result. A `cachebust` parameter busts nothing here. Read 1 hit a stale entry and read 2 missed and repopulated; yesterday's "fresh" number came from a cache miss, which is luck, not a method. Any future run that trusts a query parameter to force freshness will publish whatever the cache happens to hold.

### What read 1 was

`updatedAt 2026-10-13T20:34:15.418Z` is `2026-10-14 04:34:15 +0800` — **6 minutes 45 seconds after PR #232 merged**. A body computed inside the deploy window, when the signal source was evidently unreachable, got cached and served for the next five hours.

Its content is the problem. Not stale-but-plausible numbers, which is what yesterday found. This is the route's **fail-closed path**: `totalSignals: 0`, every confidence bucket `0`, `ece` and `brier` `null`, `calibration` `null`, `insufficientData: true`. For five hours a product whose promise is *"Every trade verified"* answered, to anyone whose request mapped to that entry, that it had **zero verified trades**.

PR #232 did not cause it in code. Checked, not assumed: `git show --stat 9ecee0a0 -- 'apps/web/app/api/calibration' 'apps/web/lib/db*' 'apps/web/lib/signals*'` returns **empty** — none of the 229 files touch the calibration route or the data layer. The deploy *event* produced the empty response; the cache made it public. Cause is recorded as the deploy window, and the code path is explicitly exonerated.

**2. "The branch has a red CI row on a branch-unique commit."** `gh run list --branch` returns `bd47e033 CI failure`, which looked like hard evidence that the branch had been tested and failed. `git merge-base --is-ancestor bd47e033 origin/main` → **true**.
